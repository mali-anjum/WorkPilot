## Found during verify
- **Resume forms dead after the first visit (fixed, re-verified)**: `App.razor` rendered `<Routes @rendermode="InteractiveAuto" />`. On a first visit Blazor Auto ran on the server circuit and the forms worked; once the WebAssembly runtime was cached, Auto picked WebAssembly, which cannot find `WorkPilot.Web.Components.Routes` (it lives in the server project), so the page stayed static and the forms submitted nothing. The resume pages were the first product pages whose actions need a live circuit, and they inject the server only `IResumesApiClient`. **Fix (app wide)**: `Routes` now renders as `InteractiveServer` instead of `InteractiveAuto` (`App.razor`, plus comment updates in `MainLayout.razor` and `AuthEndpoints.cs`). Re-verified live on repeat visits (steps above) with a smoke test of the command palette, theme toggle, Approval center and sign out.
- Noise, not a failure: the lost race `409` also writes two `fail:` entries (EF Core `Database.Command` and `Update`) with the full `WP409` stack to the Api log, although the conflict is an expected outcome.
- Existing issue, not from this feature, still present after the fix: every circuit teardown writes a `warn` plus a `fail: ...CircuitHost[111]` with `JSDisconnectedException` from `CommandPalette.DisposeAsync()` (`CommandPalette.razor:93`). With every page now on the server circuit it happens on every full page load (10 of 10 `fail` entries in the re-verify Web log); harmless for the user, but noisy.
