## Summary
A cleanup/hardening pass: `AdvanceRunJob` now recovers from a `DbUpdateConcurrencyException` instead of crashing (closing spec 0005 AC-10's known gap), the Api fails fast at startup without `ConnectionStrings:workpilotdb`, a redundant host `ShutdownTimeout` was dropped in favor of Hangfire's own, `GetJobAsync` replaced a per-link subquery with a single join, every NuGet version moved into `Directory.Packages.props` (verified byte-for-byte identical to the prior per-project versions except the already-flagged bUnit 1.40.0→2.11.3 bump), and the whole `WorkPilot.Web.Tests` suite was mechanically migrated to bUnit 2's `BunitContext`/`Render`/`AddAuthorization` API. The mechanical work (package centralization, bUnit migration, the join, docs) is clean and accurate. The one real issue is in the new `AdvanceRunJob` retry path: a concurrency conflict that lands *after* a non-idempotent tool already executed successfully gets converted into a false "Failed" step/run with no audit trail of the real outcome, and that specific path is untested (the new test only covers the idempotent-tool case).

## Major
### 🟠 Concurrency retry can misreport a successful non-idempotent action as Failed, with no audit trail, `src/WorkPilot.Workers/Agent/AdvanceRunJob.cs:33-46,112-117`
**Problem**: `AdvanceAsync` commits `Running` (line 86/109) *before* calling the tool (line 138), then does one more `SaveChangesAsync` (line 156) that adds the `ToolCall`, writes the audit row, and transitions the step to `Succeeded` — all in a single unit. If that specific `SaveChangesAsync` hits a `DbUpdateConcurrencyException` (any concurrent write to the same `AgentRun`/`AgentStep` row — both carry an `xmin` token per `AgentConfigurations.cs` — not just an approval decision on this exact step), the whole commit rolls back: the `ToolCall` row and the audit row recording the tool's real output are **both lost**, even though the tool already ran and, for a non-idempotent tool, really did whatever it does (send an email, submit an application, etc.). The outer `catch (DbUpdateConcurrencyException)` then clears the tracker and re-enqueues (line 43-44). On the fresh pass, the step reloads as `Running`; because `tool.IsIdempotent` is `false`, the `Running`-re-entry branch (line 112-117) unconditionally treats it as "died mid tool call" and calls `FailStepAndRunAsync`, marking the step and run `Failed`. The system now says the action failed, and there is no `ToolCall`/`AuditLog` row left anywhere to show it actually succeeded — the very audit trail this feature exists to provide is what got wiped by the rollback.
**Why it matters**: This is worse than the pre-existing "crash mid-execution ⇒ fail the step" tradeoff (spec 0005 AC-9), which really is undecidable from the DB. Here the actual outcome *was* knowable (the tool returned `Success`) and is discarded purely because an unrelated concurrent write touched the run's row a moment later. For a non-idempotent action (e.g. outreach, application submission) this can leave the founder believing an action didn't happen (and possibly re-triggering it) when it did, with nothing in `AuditLog` to catch the discrepancy.
**Suggested fix**: Don't let a lost race silently reclassify a tool that already reported success. Options: persist the `ToolCall`/audit row in its own small transaction immediately after the tool returns (before the status-transition save), so it survives even if the status commit later conflicts; or, on catching the concurrency exception, check whether a `ToolCall` for this step already exists before falling into the crash-recovery path, and if so, don't treat it as unexecuted. At minimum, log loudly when this happens so it isn't silent.

## Minor
### 🟡 Silent, uncapped, zero-delay re-enqueue on every concurrency conflict, `src/WorkPilot.Workers/Agent/AdvanceRunJob.cs:33-46`
**Problem**: The catch block has no logging (no `ILogger` is even injected into `AdvanceRunJob`) and no bound on how many times a single run can be re-enqueued this way. `[AutomaticRetry(Attempts = 0)]` deliberately disables Hangfire's own retry so this job would have exactly one recovery mechanism, but this new path reintroduces unlimited retries with zero backoff, just self-managed instead of Hangfire-managed.
**Why it matters**: A one-off race resolves itself fine (as the new test shows), but if conflicts become persistent (e.g. two live deliveries of the same run perpetually leap-frogging each other, or a genuine bug in a concurrency token), this becomes an invisible tight loop hammering the queue and the database with no operator signal — exactly the "silent and easy to leave on by accident" failure mode the `Hangfire:DisableServer` warning two lines below (Program.cs:115-122) was careful to avoid for a much less likely scenario.
**Suggested fix**: Log at `Warning` on this path (actor/run id), and consider a small delay or an attempt cap before giving up and surfacing the run as failed with a clear "gave up after N concurrency conflicts" reason.

## Resolution (2026-09-27)

- **Major, success misreported as Failed:** checked against the model first. Only `agent_runs` carries an `xmin` token, and a successful step's save changes only the step, so a concurrency conflict cannot hit that save; the exact race described can't happen. The same loss was reachable through a crash between the tool returning and the status save, so the fix still applies: `AdvanceRunJob` now saves the `ToolCall` and its audit row on their own (inserts only, no token) before any status change, and a `Running` step that already has a `ToolCall` is settled from it, never run again. Test: `RunAsync_WhenAStepWasLeftRunningAfterItsToolCallWasRecorded_SettlesFromTheRecordWithoutRerunning`. Spec 0005 AC-9 amended.
- **Minor, silent uncapped loop:** the conflict path now logs a warning with the run id and schedules the rerun one second later instead of at once. No attempt cap: every rerun reads fresh data and the recorded `ToolCall` stops any tool from running twice, so a loop needs another writer changing the run every second, which nothing in the product does.
- **Nit, comment:** reworded; it now says only the conflicting save is lost and earlier saves of the pass stay committed.
