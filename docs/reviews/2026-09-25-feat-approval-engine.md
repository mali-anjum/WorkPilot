## Summary
This spec-0007 change turns the spec-0005 approval stub into a real three-tier approval engine: a pure `ApprovalPolicy` domain policy, a frozen `ApprovalEvidence` snapshot captured at suspension, an `AddApprovalEngine` migration adding an optimistic-concurrency token plus evidence/columns, an Application-layer `DecideApprovalHandler`/`GetApprovalCenterHandler`, and a server-rendered `/approvals` Blazor page that posts plain antiforgery-protected forms. The work is unusually careful: the domain policy is pure and exhaustively unit tested, the decide path is guarded end to end by a real concurrency token (proven live with an actual held Postgres row lock, not a mock), and the Web/Api boundary correctly refuses to trust a client-supplied `decidedBy`. One real gap: a secondary defense-in-depth gate check in `AdvanceRunJob`'s `Running` re-entry path diverges from AC-2's contract (wrong terminal status, no audit row) on an admittedly narrow path. Everything else is nits and nice-to-haves.

## Major
### 🟠 Running re-entry gate refusal skips the AC-2 audit trail and uses the wrong terminal status, `src/WorkPilot.Workers/Agent/AdvanceRunJob.cs:101-113`
**Problem**: AC-2 says: "an approved step that no longer satisfies the policy is skipped (it never ran), its run fails, and an `ApprovalGateRefused` audit row is written instead of executing." The primary gate check (`AwaitingApproval` → `Running`, lines 79-92) implements this correctly via `RefuseAtGateAsync`: step → `Skipped`, run → `Failed`, `ApprovalGateRefused` audit row written. But the second, defense-in-depth gate check for a step found already `Running` on re-entry (its own comment cites "spec 0007, AC-2") calls `FailStepAndRunAsync` instead: step → `Failed` (not `Skipped`), and no audit row at all is written explaining why the step was killed — it looks identical to an ordinary crash-recovery failure.
**Why it matters**: This path is reachable: a step commits `Running`, the process dies before executing the tool, and before the job re-enters, the tool's `RiskTier` is redeployed to something stricter than what the approval was decided against. `PermitsExecution` then correctly returns false, but the resulting failure is indistinguishable in the audit log from "the tool timed out" — for a security-relevant control the spec calls out as the thing that "matter[s] most" for this GA feature, silently losing the "the gate refused this" signal is exactly the kind of gap an audit trail exists to prevent. It's also untested: `RunAsync_WhenAnIdempotentGatedStepIsRunningWithoutAPermittingApproval_FailsInsteadOfReexecuting` (`tests/WorkPilot.Api.Tests/AdvanceRunJobTests.cs:428-449`) only asserts step/run status and that the tool never ran — it does not check for (or rule out) an `ApprovalGateRefused` audit row, so the divergence from `RefuseAtGateAsync`'s behavior went unnoticed.
**Suggested fix**: Route this case through `RefuseAtGateAsync` (or extract its body into something both branches share) instead of `FailStepAndRunAsync`, so both gate-refusal paths agree on `Skipped` + the audit row. Add an assertion for the `ApprovalGateRefused` audit row to the existing test.

## Minor
### 🟡 `TryGetProfileId`'s 403 branch is untested, `src/WorkPilot.Web/Features/Approvals/ApprovalCenterEndpoints.cs:68-74`
**Problem**: `ApprovalCenterEndpointsTests` covers "signed out" (no auth at all → 401, verified live as a `/login` redirect) but not "authenticated with no/invalid `profile_id` claim" → 403. That branch of `TryGetProfileId` (the `Guid.TryParse(...) && profileId != Guid.Empty` check) has no test exercising it.
**Why it matters**: It's a real authorization branch on a form endpoint that decides on the user's behalf; per the test-adequacy bar (TESTS=configured, security-relevant branching logic), an untested branch here is at least a Minor even though the branch is currently unreachable through the Web app's own login flow (which always sets the claim).
**Suggested fix**: Add a case to `ApprovalCenterEndpointsTests` that signs in with the `TestSession` scheme but omits/corrupts the `profile_id` claim and asserts `403`.

## Nits
- ⚪ `src/WorkPilot.Infrastructure/Modules/Agent/Tools/DemoToolEvidence.cs:26-36`, the "active resume, else newest resume" fallback actually picks the newest *version row* across all of the profile's resumes when none is active, which can differ from "the newest resume's newest version" if an older resume has a more recently created version than a newer resume. Harmless since these are inert demo tools whose evidence is illustrative only (per the spec, real tools pin their own version ids), but worth a comment if it's ever cargo-culted into a real tool.
- ⚪ `src/WorkPilot.Infrastructure/Modules/Approvals/ApprovalRepository.cs:27`, `LoadForDecisionAsync` uses `FirstAsync` (throws) to load the run after already using the softer `FirstOrDefaultAsync`-then-null-check pattern for the step just above it; an orphaned step (FK violation aside) would surface as an unhandled 500 rather than the same graceful `NotFound` the sibling check produces. Very unlikely to occur given the schema's foreign keys, but the inconsistency stands out.

## Strengths
- The domain policy (`ApprovalPolicy`) is small, pure, and exhaustively tested, including the two "who's stricter" edge cases (tool tier tightened after approval, approval's recorded tier tightened after the tool loosened) and the unknown-tier-defaults-to-strictest fallback — real defense-in-depth thinking, not just happy-path coverage.
- The concurrency story is genuinely proven, not assumed: `Decide_WhileAnotherTransactionChangesTheRun_Returns409AndLeavesNoPartialState` holds a real uncommitted Postgres transaction against `agent_runs` and asserts the decide request blocks, loses, and leaves zero partial state (no audit row, approval still `Pending`), then confirms a retry succeeds.
- The trust boundary is handled correctly and is tested for it: the Web decide endpoint always derives `decidedBy` from the session's `profile_id` claim, and `A_forged_profile_in_the_form_is_ignored` proves a spoofed form field is discarded.
- Migration and `WorkPilotDbContextModelSnapshot` are consistent (the `Status` concurrency token needs no schema change and correctly has none; the three added columns and the new index match exactly).

## Test coverage
Strong and matches the acceptance criteria one-to-one: `ApprovalPolicyTests` covers AC-1/2/8 in the domain with no infrastructure; `AdvanceRunJobTests` adds six new cases covering suspension, evidence capture (including the evidence-provider-throws path), auto-allowed bypass, and both gate-refusal paths against a real Postgres; `ApprovalEndpointsTests` covers AC-4/7/8/9/10 including the live concurrency race; the three Web test files cover the page (AC-5), the form-post trust boundary and antiforgery (AC-6), and the client's status-code mapping. The two gaps found above (the Running-reentry gate's audit behavior, and the Web decide endpoint's missing-claim 403 branch) are the only uncovered pieces of consequence; everything else claimed done in `verify.md` was exercised.

## Resolution (2026-09-25)
- Major, fixed: the `Running` re-entry refusal now goes through `RefuseAtGateAsync` and writes the same `ApprovalGateRefused` audit row. The step ends `Failed`, not `Skipped`: the domain doesn't allow `Running` → `Skipped`, and a step that was already `Running` may have partly run, so `Skipped` ("never ran") would be untrue. Spec 0007 AC-2 now states both paths. Tests assert the audit row with and without an approval row.
- Minor, fixed: `ApprovalCenterEndpointsTests` now covers a signed in session with a missing, malformed, or empty `profile_id` claim (`403`, nothing decided).
