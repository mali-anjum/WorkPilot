## Summary

This change builds the agent orchestrator core end to end per spec 0005: `ITool`/`ToolRegistry`/`PolicyEngine`/`VerificationEngine` in Domain/Application, `AuditService`/`WorkflowMirror`/two milestone tools in Infrastructure, `PlanRunJob`/`AdvanceRunJob` in Workers, `ChatClientPlanner`/`FakeChatClient` in AI, and three internal endpoints in `Program.cs`. The restart-survival and retry-exhaustion logic (AC-8, AC-9) is well designed and directly tested against a real Postgres. However, two real defects survive: the decide endpoint always audits the approval decision as actor `"Agent"` instead of the deciding profile (contradicts the spec's own data-mapping table), and the decide endpoint's `AwaitingApproval → Running` transition collides with `AdvanceRunJob`'s crash-recovery check, so any future non-idempotent approval-required tool will always fail immediately after approval — a latent but certain bug hidden only because the one shipped approval tool happens to be idempotent. AC-2 (policy rejection) also has no test anywhere in the diff.

## Major

### 🟠 Approval decision audited as actor "Agent", not the deciding profile, `src/WorkPilot.Api/Program.cs:241`
**Problem**: `audit.Record("Agent", $"Approval{newStatus}", ApprovalTargets.AgentStep, step.Id, null)` hardcodes the actor to `"Agent"` for the approval *decision* audit entry. The spec's own value-sourcing table (docs/specs/0005-agent-orchestrator-core/index.md, "Value sourcing", row `Every ToolCall, and every Approval create/decide` → `AuditLog.Actor`) explicitly distinguishes: `"Agent"` for a tool call and for an approval's *creation*, but **the deciding `ProfileId`** for its *decision*. `request.DecidedBy` is available in scope but never used for the audit actor (it's only written to `Approval.DecidedBy`).
**Why it matters**: The whole point of this audit trail per the user story ("so I can see exactly what the agent did and why") is knowing who did what. Right now every decision — approve or reject, by whichever profile — is indistinguishable from an autonomous agent action in the audit log, even though `Approval.DecidedBy` correctly records the real actor on the `Approval` row itself. This is a real, unit-testable deviation from the written spec, not a style preference.
**Suggested fix**: Pass `request.DecidedBy.ToString()` (or the profile's stable identifier) as the actor for this `audit.Record` call, keeping `"Agent"` only for the `ToolCall` and `Approval`-creation audit entries as the spec describes.

### 🟠 Decide-then-Running race: a non-idempotent approval-required tool can never succeed after approval, `src/WorkPilot.Api/Program.cs:246` and `src/WorkPilot.Workers/Agent/AdvanceRunJob.cs:72-77`
**Problem**: On `Approve`, the decide endpoint transitions the step straight to `AgentStepStatus.Running` (Program.cs:246) *before* `AdvanceRunJob` ever executes it, then enqueues `AdvanceRunJob` (Program.cs:260). When that job picks the step up, it finds `Status == Running` and enters the `case AgentStepStatus.Running when !tool.IsIdempotent` branch (AdvanceRunJob.cs:72-77), whose comment says "a prior invocation of this job died mid-execution" — but here the step was never actually executed even once; it's `Running` only because `Decide` forced it there. For a non-idempotent tool this unconditionally calls `FailStepAndRunAsync`, so the step (and the whole run) fails immediately, every time, regardless of the actual approval outcome. `tests/WorkPilot.Api.Tests/AdvanceRunJobTests.cs`'s `RunAsync_WhenANonIdempotentStepIsFoundRunningOnReentry_FailsItInsteadOfReexecuting` test independently confirms this exact code path fires for any `Running` + non-idempotent combination, with no way to distinguish "crashed mid-execution" from "just approved, not yet run."
**Why it matters**: The only reason this doesn't show up today is that `ApprovalRequiredDemoTool.IsIdempotent` is `true` (ApprovalRequiredDemoTool.cs:19), which happens to route through the safe `case AgentStepStatus.Running: break;` branch instead. The moment a real approval-required tool is added that is *not* idempotent — which is the realistic case for the domain agents this milestone exists to unblock (e.g. "submit an application", "send an email" — exactly the examples `ToolRiskTier.ApprovalRequired`'s own doc comment gives) — every single approval will complete successfully at the API layer (`resumed: true`, `Approval.Status = Approved`) while the actual step and run fail right after, silently, with no error surfaced to the approver. AC-4 and AC-9 individually pass their own tests, but their combination is broken.
**Suggested fix**: Don't reuse `AgentStepStatus.Running` to mean both "approved, ready to execute" and "died mid-execution." Either (a) give `AdvanceRunJob` a way to tell these apart (e.g. only apply the non-idempotent-fails-on-Running rule when the step was already `Running` *before* this job invocation started, or track a separate "approved, not yet started" marker), or (b) have `AdvanceRunJob` — not the decide endpoint — perform the `AwaitingApproval → Running` transition immediately before it calls `tool.ExecuteAsync`, mirroring exactly how the `Pending → Running` path already works for auto-allowed tools (AdvanceRunJob.cs:66-70). Option (b) looks like the smaller, more consistent change: have `Decide` transition the step back to `Pending` conceptually resumed for execution (or add a dedicated `Approved` step status) and let `AdvanceRunJob` own every `→ Running` transition.

## Minor

### 🟡 AC-2 (policy rejection) has no test coverage anywhere in this diff
**Problem**: `PolicyEngine.Validate` (src/WorkPilot.Application/Modules/Agent/PolicyEngine.cs) — the code path that rejects an unknown tool name or a step missing a required argument — is not exercised by any test in `tests/WorkPilot.Domain.Tests/AgentOrchestratorTests.cs`, `tests/WorkPilot.Api.Tests/AgentOrchestratorEndpointsTests.cs`, `AdvanceRunJobTests.cs`, or `ChatClientPlannerTests.cs`. Since the shipped `FakeChatClient` only ever emits plans that reference real, correctly-argued tools, this path also has no live coverage via `/check verify`.
**Why it matters**: AC-2 is one of the ten acceptance criteria this whole spec is built to satisfy ("if any planned step fails this check, the whole run fails before any step executes"), and it is entirely branching/validation logic — exactly the category the review guide calls out as at least a Minor gap, Major if security relevant. A regression here (e.g. someone loosens `PolicyEngine.Validate` or `PlanRunJob`'s handling of `violations.Count > 0`) would ship silently.
**Suggested fix**: Add a `PolicyEngine` unit test (unknown tool name, missing required argument) and/or a `PlanRunJob`-level or endpoint-level test that seeds a plan violating policy and asserts the run reaches `Failed` without any `AgentStep` executing.

### 🟡 `AgentRun`'s `xmin` concurrency token has no handling for the conflict it's meant to detect
**Problem**: `AgentRunConfiguration` (src/WorkPilot.Infrastructure/Persistence/Configurations/AgentConfigurations.cs:57-61) correctly wires Postgres's `xmin` as an EF Core concurrency token for AC-10's "lost update" guard, but neither `AdvanceRunJob.RunAsync` nor the decide endpoint in `Program.cs` catches `DbUpdateConcurrencyException` around their `SaveChangesAsync` calls that mutate `AgentRun`.
**Why it matters**: The token will correctly *prevent* a silent lost update, but a genuine concurrent conflict (a step-advance job and an approval decision landing on the same run at the same instant) will surface as an unhandled exception — a 500 from the decide endpoint, or an unobserved Hangfire job failure — rather than a clean, intentional outcome. AGENTS.md notes the project hasn't chosen its API error-handling pattern yet, so this may be an acceptable placeholder, but it's worth flagging now since AC-10 frames the token as the actual concurrency *defense*, not just a passive column.
**Suggested fix**: At minimum, note this as a known gap (or catch `DbUpdateConcurrencyException` and retry/return 409) when the project's error-handling pattern is decided; not necessarily a blocker for this milestone given AGENTS.md's own "not yet chosen" caveat.

## Strengths

- The restart-survival design (`AgentStep.Status` in the database as the sole resumption cursor, `[AutomaticRetry(Attempts = 0)]` on both jobs to avoid a second, disagreeing recovery mechanism) is exactly what the spec calls for, and `AdvanceRunJobTests.cs` proves the retry-exhaustion and non-idempotent-crash-recovery branches directly against real Postgres rather than mocking the database.
- `AuditService.Record` (Infrastructure) and every call site consistently pairs a `ToolCall`/`Approval` mutation with an audit write in the same unit of work, matching AC-5's "every ToolCall and Approval create/decide has exactly one AuditLog entry" invariant; tests cover the JSON-hostile-error-text and null-payload edge cases explicitly.
- AC-6 (no secret/`ProfileId` leakage to the Planner) is respected cleanly: `PlanRunJob` passes only `ToolDescriptor`s and the goal string to `IPlanner.PlanAsync`, and `ProfileId` is injected into `ToolExecutionContext` only inside `AdvanceRunJob`, never through the LLM boundary.
- `ChatClientPlannerTests.cs` is a good pure-unit complement to the live-stack tests: it exercises the parse-retry-then-fail branch (AC-7) that the deterministic `FakeChatClient` can never trigger through `/check verify`.

## Test coverage

Well covered: AC-1/AC-3/AC-5/AC-6 (trigger + happy path), AC-4/AC-10's decision race (approve/reject/409/404), AC-7 (planner retry-then-fail, both success-after-retry and fail-after-retry), AC-8 (retry exhaustion, no later step executes), and AC-9's two crash scenarios (idempotent vs non-idempotent `Running` re-entry) — all against a real Postgres via `SharedApiFactory`/`AdvanceRunJobTests`, consistent with AGENTS.md's "integration tested against real systems" rule.

Gaps: AC-2 (policy rejection) has zero test coverage, live or automated (see Minor finding above). There is also no test asserting the decide endpoint's audit `Actor` value, which is exactly the kind of assertion that would have caught the Major finding above — worth adding alongside the fix.
