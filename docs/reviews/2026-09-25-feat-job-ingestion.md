## Summary
This adds job source ingestion end to end per spec 0008: a source-agnostic `IJobSource` seam, a shared domain normalizer, `Job.Create`/`Refresh` upsert rules, a Greenhouse adapter, a Hangfire job, and two internal endpoints, backed by a migration that adds `Description`/`PostedAt` to `jobs` and `JobSourceId`/`ExternalId` to `job_snapshots`. The implementation is careful: normalization is deterministic, the upsert is idempotent and atomic (one `SaveChanges` per run), board tokens are validated twice against a strict regex before touching a URL, and the migration's backfill matches the model snapshot exactly. Test coverage is strong (unit tests for the normalizer/entities, real-Postgres integration tests with a scripted source, and a captured-payload adapter test), and the feature was proven live against the real Greenhouse API. The one real gap is a half-built safety net around soft-deleted jobs that the repository's own comment describes but the domain layer doesn't implement (currently unreachable, since nothing in this feature soft-deletes a `Job` yet).

## Minor
### 🟡 `Job.Refresh` never un-deletes a soft-deleted job, so `JobIngestionRepository`'s duplicate-prevention comment is only half true, `src/WorkPilot.Domain/Modules/Jobs/Entities.cs:72`
**Problem**: `JobIngestionRepository.GetJobsByExternalIdAsync` (`src/WorkPilot.Infrastructure/Modules/Jobs/JobIngestionRepository.cs:33-41`) deliberately calls `.IgnoreQueryFilters()`, with a comment explaining that "a soft deleted job still owns its `(source, external id)` slot under the unique index, so it must be found and refreshed, never re-inserted as a duplicate." That query does find a soft-deleted job and route it into `Job.Refresh` — but `Refresh` (`Entities.cs:72-99`) never clears `IsDeleted`/`DeletedAt`, and `SoftDeletableEntity` (`src/WorkPilot.Domain/Common/EntityBase.cs`) exposes no "undelete" operation at all. So a job that was ever soft-deleted would be silently updated on every future re-ingestion (new snapshots, refreshed fields) while staying invisible forever to `GET /internal/jobs` and anything else that respects the global `IsDeleted` query filter (`WorkPilotDbContext.cs:118-130`) — it can never come back, only rot in place.
**Why it matters**: Right now this is unreachable — nothing in this PR or the rest of the codebase ever calls `Job.SoftDelete`, so no `Job` row can currently be in this state. But it's clearly intentional forward-looking code (the comment names the exact scenario), and the "stale jobs" follow-up in spec 0008 (`docs/specs/0008-job-source-ingestion/index.md:133`) is exactly the kind of feature that will start setting `IsDeleted = true`. Once it lands, this half-implemented safety net will produce jobs that silently stop reappearing after a source un-deletes them, without any error or signal.
**Suggested fix**: Either give `Job` (or `ISoftDeletable`) a way to clear `IsDeleted`/`DeletedAt`, and have `Refresh` call it, or narrow the repository's comment/`IgnoreQueryFilters` to what's actually implemented today and add a TODO pointing at the stale-jobs follow-up so the gap isn't rediscovered from scratch.

## Nits
- ⚪ `src/WorkPilot.Domain/Modules/Jobs/Ingestion.cs:197`, the `Whitespace()` regex explicitly lists `\xa0` (NBSP) alongside `\s`; .NET's `\s` already matches NBSP (Unicode `Zs` category), so it's redundant (harmless, and `​` for zero-width space is a genuine addition since that's category `Cf`).
- ⚪ `src/WorkPilot.Api/Endpoints/JobsEndpoints.cs:39-48`, `TriggerIngestionAsync` returns a bare `Results.BadRequest()` for three different failure reasons (missing fields, unknown source, invalid board token) with no problem detail distinguishing them; fine for now per the spec's own follow-up ("revisit when the project wide error pattern is decided"), just flagging it's the same shape noted there.

## Strengths
- The migration's `Up()` backfill (`left(j."ExternalId", 200)` before adding the FK) exactly matches what the regenerated `WorkPilotDbContextModelSnapshot.cs` expects — checked line by line, no drift between the two.
- `JobSearchQuery`/`JobNormalizer`/`Job.Create`/`Job.Refresh` keep every business rule in the domain layer; `JobIngestionService` is a thin orchestrator that only sequences fetch → filter → normalize → upsert → audit → save, consistent with AGENTS.md's Clean Architecture rule.
- Idempotency is well tested end to end: `tests/WorkPilot.Api.Tests/JobIngestionTests.cs` proves a same-content re-run only advances `VerifiedAt` (no new snapshot, no new job) and a changed-content re-run updates exactly one job and adds exactly one snapshot, matching AC-4 precisely.
- `GreenhouseJobSource.Describe` validates the board token against `^[a-z0-9_-]{1,100}$` before it ever reaches a URL, and `FetchAsync` re-validates the token pulled back out of stored `Config` — real defense in depth against a config row being tampered with or malformed, with tests for both the happy path and the rejection cases (`../other`, `a/b`, `evil.test`, `board?x=1`).
- The single shared `JobNormalizer` (deterministic hash, stable whitespace/HTML handling) is exercised with good edge cases: entity-encoded HTML, `&nbsp;`, non-breaking/zero-width whitespace, and a locale-correct UTC conversion for `PostedAt`.
