## Summary

This change closes out the foundational stack slice: it replaces a no-op `EnsureCreatedAsync` with real EF Core migrations behind `GET /health/db`, adds the `InitialCreate` migration, makes the Hangfire background worker server skippable via `Hangfire:DisableServer` so `WebApplicationFactory` teardown stops hanging, and lands the repo's first xUnit integration test project. The bug-hunting behind it is genuinely good work — the `EnsureCreatedAsync` diagnosis and the refusal to loosen the Hangfire dashboard's real authorization for test convenience are both the right instincts, and the code comments explain *why* rather than *what*.

The headline problem is a committed credential: `HealthDbEndpointTests.cs:36` hardcodes the live Supabase Postgres password, the exact value the repo's own `.gitignore` goes out of its way to keep out of version control. Beyond that, running `Database.MigrateAsync()` inside an unauthenticated request handler is a real production hazard, the `Hangfire:DisableServer` gate fails silently in the wrong direction, and the new EF tables land in Supabase's shared `public` schema, which sits uneasily with the spec's schema-ownership boundary.

## Blockers

### 🔴 Live database password hardcoded in committed test source, `tests/WorkPilot.Api.Tests/HealthDbEndpointTests.cs:35-36`

**Problem**: `DefaultLocalConnectionString` embeds `Password=TJm35NQR8PfbdaDfwfbPo5lhjWZUJ2mP` in source. This is the self-hosted Supabase stack's real Postgres superuser password from `supabase/.env` — a file the repo's `.gitignore` explicitly excludes under the comment "Supabase self-hosted stack: never commit real secrets". The test project is wired into `WorkPilot.slnx`, so this ships to every clone and to git history permanently.

**Why it matters**: It directly defeats a secret-hygiene control the project deliberately put in place, and it is the `postgres` superuser on the database that also holds Supabase's `auth.*` schema (user records, password hashes, refresh tokens). Once committed, rotation is the only real remedy — deleting the line later does not remove it from history. If this repo is ever pushed to a remote, or the same password is reused on the VPS deployment the spec describes, this is a credential disclosure.

**Suggested fix**: Remove the literal entirely. Require the connection string from configuration — `WORKPILOTDB_CONNECTION` (already supported), user-secrets, or a `.runsettings`/`appsettings.Test.json` that is gitignored — and have the test fail with a clear, actionable message when it is absent rather than falling back to a baked-in credential. Then rotate the Supabase Postgres password, since it must now be treated as exposed. If a zero-config local default is genuinely wanted, make it a credential that is worthless by construction (a throwaway ephemeral container via Testcontainers, or a documented dev-only password that is not the one guarding the real auth schema).

## Major

### 🟠 Schema migrations run on every request to an unauthenticated health endpoint, `src/WorkPilot.Api/Program.cs:71-80`

**Problem**: `GET /health/db` calls `await db.Database.MigrateAsync()` on every single request. Switching off `EnsureCreatedAsync` was correct, but the fix put schema migration in the request path rather than moving it to startup or an explicit out-of-band step.

**Why it matters**: Three distinct problems in production. (1) It is DDL triggered by an anonymous, unauthenticated HTTP GET — anyone who can reach the endpoint can force migration work, and there is no rate limit; a burst of concurrent calls means concurrent `MigrateAsync` invocations racing on `__EFMigrationsHistory`, which Postgres advisory locking mitigates but does not make free. (2) A health check should be a cheap, read-only liveness probe; orchestrators and Aspire poll these on a timer, so this makes every poll attempt a migration check against the database. (3) When a future migration is slow or fails, the failure surfaces as a 500 on a health endpoint rather than as a deployment failure, which is exactly backwards — the deploy succeeds and the app reports unhealthy.

**Suggested fix**: Move migration to a one-shot step outside request handling — a startup task/`IHostedService` guarded to non-production, an Aspire migration-worker project, or an explicit `dotnet ef database update` in the deploy pipeline. Leave `/health/db` as a pure read (the `ScaffoldPings.CountAsync()` round-trip alone already proves what AC-5 asks for). Note the comment at lines 72-76 still explains why `EnsureCreatedAsync` is wrong without saying why migrating *here* is right; update it once the call moves.

### 🟠 `Hangfire:DisableServer` fails silently toward "no background processing", `src/WorkPilot.Api/Program.cs:41-50`

**Problem**: The gate is `if (!builder.Configuration.GetValue<bool>("Hangfire:DisableServer"))`. Any environment where that key is accidentally set truthy — a stray `Hangfire__DisableServer` env var on the host, a copied compose file, a leftover from a test run in the same shell — starts the API with the dashboard and client API fully functional but **no worker consuming the queue**. Nothing is logged either way.

**Why it matters**: This is the worst failure shape for a job system: enqueues succeed, the API returns 200, the dashboard renders normally, and jobs simply accumulate unprocessed. Per the spec, Hangfire is the durable-workflow substrate for the agent orchestrator, so a silent worker outage means approvals and agent runs queue up invisibly until someone notices by hand. The default direction is right (server on unless disabled), but there is no signal when the non-default path is taken.

**Suggested fix**: Log explicitly at startup on both branches — a warning-level "Hangfire background server disabled by configuration" when skipped — so the condition is visible in logs and in the Aspire dashboard. Consider additionally refusing the flag outside Development/Testing (throw or force-enable in Production), so this can never be the production state. Also worth adding a readiness/health check that asserts a worker server is registered when it is supposed to be.

### 🟠 EF Core tables land in Supabase's shared `public` schema, `src/WorkPilot.Infrastructure/Persistence/Migrations/20260920161620_InitialCreate.cs:15-27`

**Problem**: `scaffold_pings` (and `__EFMigrationsHistory`) are created with no schema specified, so they go to `public` in the same `postgres` database Supabase owns. `WorkPilotDbContext`'s own doc comment states EF "is scoped to the product's own schema only", but no schema is actually configured — the migration does not honor the boundary the comment claims.

**Why it matters**: `public` is the schema Supabase's PostgREST exposes over HTTP by default. PostgREST and Kong are currently deferred (per `supabase/docker-compose.yml`), so nothing is exposed today — but the spec's whole architecture anticipates adding them, and on that day every EF-owned product table becomes reachable through the Supabase anon/service keys unless RLS is correct on each one. Fixing this after the real 30+ entity data model lands (foundation.md item 3) means a schema-move migration across the entire model; fixing it now costs one line while there is exactly one placeholder table.

**Suggested fix**: Set an explicit default schema on the DbContext (`modelBuilder.HasDefaultSchema("workpilot")`) and configure the migrations history table into it, then regenerate `InitialCreate`. Record the chosen schema name in spec 0001 alongside the existing "EF never touches `auth.*`/`storage.*`" rule, so the boundary is stated in both directions.

## Minor

### 🟡 Test setup mutates process-global environment variables and never restores them, `tests/WorkPilot.Api.Tests/HealthDbEndpointTests.cs:49-53`

**Problem**: `CreateFactory()` calls `Environment.SetEnvironmentVariable` for both the connection string and `Hangfire__DisableServer`. These are process-wide and never reset. The comment at lines 41-48 correctly explains *why* env vars are the only lever (`WebApplication.CreateBuilder` reads config before `WithWebHostBuilder` layers anything on), so the mechanism is justified — the problem is the lack of scoping.

**Why it matters**: xUnit runs test collections in parallel within an assembly. Today there are two tests in one class so the writes are idempotent and harmless, but the moment a second test class is added — especially one that *needs* the Hangfire worker running — it will inherit `Hangfire__DisableServer=true` set by whichever class ran first, and fail or pass for reasons invisible in its own source. This is the kind of cross-test coupling that costs an afternoon to diagnose later.

**Suggested fix**: Hoist the setup into a shared `IClassFixture`/`ICollectionFixture` that owns the factory, sets the variables once in its constructor and clears them in `Dispose`, and have tests take the fixture rather than each constructing a factory. That also stops the app being booted twice for two tests.

### 🟡 Tests hard-fail with an opaque error when Postgres is not running, `tests/WorkPilot.Api.Tests/HealthDbEndpointTests.cs:62-85`

**Problem**: Both tests require a live Supabase Postgres on `localhost:5433`. With nothing listening, the failure surfaces as an Npgsql connection exception wrapped in a 500 from the endpoint, and the assertion message reads as "expected OK, got InternalServerError" — which points at the app, not at the missing prerequisite.

**Why it matters**: This is the first test project in the repo and sets the pattern. In CI, or on a fresh clone where `docker compose up` has not been run, the suite fails in a way that looks like a product bug. The file comment documents the prerequisite, but nothing enforces or reports it at runtime.

**Suggested fix**: Probe the connection in the fixture and either skip with an explicit reason or fail with a message naming the prerequisite ("requires the self-hosted Supabase stack on port 5433; run `docker compose up` in `supabase/`"). Longer term, Testcontainers would remove the ambient dependency entirely and would also dissolve the hardcoded-credential blocker above.

### 🟡 The dashboard test cannot detect the regression it appears to guard, `tests/WorkPilot.Api.Tests/HealthDbEndpointTests.cs:15-26, 76-85`

**Problem**: The `IStartupFilter` forces `RemoteIpAddress = IPAddress.Loopback` on *every* request, then `HangfireDashboard_IsReachable` asserts `/hangfire` returns 200. The pattern itself is sound and I would not call it a smell — the reasoning in the comment is correct, and simulating what a real loopback request looks like is strictly better than swapping in a permissive dashboard auth filter for tests. But the resulting test asserts only "the dashboard is mapped", not "the dashboard is protected".

**Why it matters**: If someone later replaces the default local-only filter with an allow-all filter — a very common shortcut when the dashboard needs to be reachable from a browser on a VPS — this test still passes. Given the `Program.cs:66-68` TODO explicitly anticipates that this authorization story is unfinished, the one test touching it should be the thing that notices.

**Suggested fix**: Add a companion test without the startup filter (or with a non-loopback address) asserting `/hangfire` returns 401/403. That pins the actual security property and makes the loopback filter's purpose self-evident from the pair.

### 🟡 Host-wide 5s shutdown timeout is broader than the problem it solves, `src/WorkPilot.Api/Program.cs:8-11`

**Problem**: `ShutdownTimeout = TimeSpan.FromSeconds(5)` is set on the host, in addition to the (well-justified) 5s on the Hangfire server itself at line 48. The comment frames it as being about Hangfire's dispatchers, but it applies to everything the host drains on stop.

**Why it matters**: In production this caps the grace period for *all* in-flight HTTP requests, not just Hangfire. Dropping from the 30s default to 5s means any request still running at shutdown — a long agent step, a slow external API call, an upload — is cut off mid-flight on every deploy and container restart. Now that the Hangfire server has its own explicit timeout, the host-level one is mostly redundant.

**Suggested fix**: Either remove the host-level override and rely on the Hangfire-specific one, or raise it to something that accommodates real request drain (15-30s) and update the comment to say it is a deliberate deploy-latency tradeoff rather than a Hangfire workaround.

### 🟡 Transitive package version conflict papered over per-project, `tests/WorkPilot.Api.Tests/WorkPilot.Api.Tests.csproj:13-17`

**Problem**: A direct `Microsoft.EntityFrameworkCore.Relational` 10.0.12 reference exists solely to force a transitive 10.0.11 (via `Mvc.Testing`) up to match the app. The comment explains it well and the fix works, but it is a local patch to a solution-wide problem.

**Why it matters**: The comment notes the mismatch broke migrations at runtime with a silent 500 — that is a nasty class of failure, and the same mismatch will recur in the next test project or whenever a package bumps. Solving it once centrally is strictly cheaper than rediscovering it per project.

**Suggested fix**: Add `Directory.Packages.props` with central package management (`ManagePackageVersionsCentrally`), pinning EF Core and its Relational/Npgsql companions solution-wide. This is also a natural item for the not-yet-started "Coding standards & tooling" scope entry.

## Nits

- ⚪ `tests/WorkPilot.Api.Tests/HealthDbEndpointTests.cs:72-73`, asserting on raw JSON substrings (`"\"status\":\"ok\""`) is brittle against serializer settings (casing policy, whitespace, property order). Deserialize into a record or parse with `JsonDocument` and assert on typed values.
- ⚪ `tests/WorkPilot.Api.Tests/HealthDbEndpointTests.cs:73`, `Assert.Contains("\"scaffoldPings\":", body)` asserts only that the key exists, not that the count is a number or non-negative. Assert the parsed value's type at minimum.
- ⚪ `src/WorkPilot.Api/Program.cs:72-76`, the comment explains what `EnsureCreatedAsync` *would* do, but that call is gone — it reads as archaeology. Keep the insight (it is valuable) but reframe it as the rationale for the current approach, or move it to the spec's Consequences section.
- ⚪ `src/WorkPilot.Api/Program.cs:66-68`, the dashboard auth TODO lives only in a code comment. Given it is a genuine pre-deployment gate, mirror it as an unchecked item in `docs/scope/foundation.md` so it cannot be shipped past silently.
- ⚪ `src/WorkPilot.Api/Program.cs:30`, `GetConnectionString("workpilotdb")` can return null; it is passed straight into `UseNpgsqlConnection`, where a missing connection string surfaces as a less obvious failure than an explicit startup guard would.

## Strengths

- **The `EnsureCreatedAsync` diagnosis is excellent.** Recognizing that it silently no-ops when the *database* exists but EF's tables do not — a genuinely subtle trap made worse here by Supabase pre-creating `postgres` — is the kind of bug that usually survives to production. The fix direction (real migrations, checked-in `InitialCreate`) is right, even though the placement needs work.
- **Refusing to loosen the Hangfire dashboard's authorization for the test.** Simulating a real loopback request via `IStartupFilter` instead of swapping in a permissive auth filter is the disciplined choice, and it keeps the production authorization path exactly as it ships. This is a pattern worth keeping, not a smell.
- **The comments explain *why*, consistently.** `Program.cs:36-40`, the config-timing explanation at `HealthDbEndpointTests.cs:41-48`, and the package-conflict note in the csproj all capture non-obvious reasoning that would otherwise be lost. The `WorkPilotDbContext` doc comment even tells future authors not to add entities there yet. This is above-average for scaffold code.
- **Each fix is a real fix, not a test-side workaround.** The scope note lists three bugs found while writing tests, and all three were corrected in the product code. That is the right instinct and it is visible in the diff.
- **Test project wiring is correct out of the gate** — registered in `WorkPilot.slnx` under a `/tests/` folder, `IsPackable=false`, `InternalsVisibleTo` on the API for `WebApplicationFactory<Program>` against top-level statements. No "tests pass locally but CI discovers zero" trap here.

## Test coverage

This diff *is* the repo's first test project, so the absence of a prior testing convention is noted once here rather than charged against the change: there is no `test-preferences.json`, no CI test step, and no documented runner expectation. That gap belongs to the "Coding standards & tooling" scope item and should be closed before the data model feature starts, since correctness findings currently have no automated safety net catching them.

What the two new tests cover is well chosen — `GET /health/db` exercises a real EF Core round-trip against live Postgres (AC-5) and `/hangfire` proves dashboard reachability (AC-6), which is genuinely the only non-boilerplate behavior in the scaffold.

What is not covered, in rough priority order:

- **The `Hangfire:DisableServer` branch itself is untested in its default (enabled) state.** Every test sets it to `true`, so the production path — worker server actually registered and processing — is never exercised. Given this is new branching configuration logic controlling whether background work happens at all, that is the most consequential gap in the diff.
- **Dashboard *rejection* of non-loopback requests**, per the Minor finding above. The security property is asserted nowhere.
- **`/health/db` failure behavior** when the database is unreachable or a migration fails. The endpoint currently has no error handling, so it returns an unhandled 500 with whatever the framework chooses to leak; no test pins what a caller should see.
- **The `InitialCreate` migration's `Down` path** is never executed. Low stakes for a single placeholder table, but worth a round-trip check once the real data model lands.
